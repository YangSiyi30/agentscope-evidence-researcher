## 1. 先准备一段准确的项目介绍

### Q01：用30秒怎样介绍这个项目？

> 我参考开源研究助手的思路，用AgentScope实现一个单Agent资料研究流程。模型根据问题决定搜索、读取已知来源或回答；应用在工具入口控制预算、来源资格和错误，分别保存搜索摘要、有限正文、引用与执行记录。我重点做了证据分层、失败后的状态一致性、可复现边界测试，以及便于演示的终端入口。

这段介绍包含“解决什么问题、谁做决定、程序怎样约束、怎样证明”的完整链条。不要只说“接入大模型和搜索”，因为这不能说明为什么需要Agent，也不能体现你写了什么规则。

如果被追问“deep research到底有多deep”，应说明它是有界的研究原型：可以多轮取证、读来源并回答，但不是大型商业研究系统，也没有无限自主规划、完整学术综述或事实准确率承诺。

### Q02：哪些来自开源，哪些是自己的贡献？

上游提供研究助手的参考思路；AgentScope提供Agent、模型适配、消息、Toolkit与循环；MCP、HTTPX、Playwright等提供协议或底层能力。这些不能称为自己从零发明。

本地贡献是围绕任务补足应用规则：`ResearchSession`的来源与预算、失败也计尝试、查询去重、读页资格、摘要/正文分层、读页元数据校验、先验证后提交、诊断与测试、保存和查看结果。面试时宜说明是在AI协助下完成，再用代码、反例和测试证明自己能理解和维护。

一个可验证的贡献比“自研智能体平台”更有说服力。比如“坏搜索批次以前会留下半条成功证据；现在整批校验后提交，失败时新增证据为0”，可以直接用同输入前后对照解释。

### Q03：它实现了Memory、RAG或多Agent吗？

本项目有**单次任务的上下文与会话状态**。框架保存本题的消息，Session保存本题来源、正文和预算；换一个问题会创建新Session。这不等于跨任务长期记忆、用户画像或断点续跑。

它使用外部资料增强回答，可以说明具有检索增强思路；但没有把文档切块入库、计算embedding、建立向量索引，因此不应说成完整向量RAG系统。两个工具、多个进程或多次模型调用，也不等于多个研究Agent。

### Q04：本科面试应该把重点放在哪里？

优先讲清一个完整问题的流动：输入怎样成为模型消息，工具请求怎样执行，失败怎样返回，证据怎样保留，为什么输出检查不能保证事实正确。然后选一个实际修复深入解释。

不用先学LangGraph、向量数据库或原学习图阶段7来补齐名词。若岗位另有部署、数据库、多Agent协作要求，可以承认这些不在当前实现范围，再讨论一个有需求依据的扩展。

## 2. 五分钟面试演示：脚本与追问放在一起

### 第一分钟：介绍问题并画核心循环

先说Q01的30秒介绍，再画下面的线：

```text
问题与工具说明 → 模型响应
                  ├─ 要调用工具 → SDK校验/分发 → Session硬规则
                  │                            ├─ 允许：实际后端 → 保存证据
                  │                            └─ 拒绝/失败：结构化说明
                  │                ← 工具结果回到上下文 ←
                  └─ 给出回答 → 完成/引用/长度检查 → 保存
```

图中最重要的是**工具结果回到下一轮模型**，以及“模型提出动作”和“程序允许执行”之间的分工。终端菜单与文件打开是循环外的操作，不要从启动脚本一路背到每一个辅助函数。

### 第二分钟：运行固定搜索与读页

在项目PowerShell执行：

```powershell
.\start.bat
```

依次选择离线1、local1、推荐预算1、预设1、开始1；可一路回车。也可使用等价命令：

```powershell
uv run --offline --no-sync as-research "解释检索相关性与事实支持的区别" --scenario tool_chain --reader http --searches 1 --pages 1 --strict
```

终端会直接显示保存的回答。本例通常是3次固定模型调用、2条应用工具记录、1次搜索尝试、1次读页、1份正文。选择结果菜单2看trace；6直接看run.json；3/4/5可隔离打开报告、JSON或目录。

这里必须主动说明：模型决定和资料是固定的，真实执行的是Agent/Toolkit/Session接线，不能用它证明真实模型的理解能力。即使离线输入自己的问题，仍是固定响应演示。

需要展示MCP时只把传输改为2，或命令加`--transport mcp`。此时多出2次RPC，但业务仍是2次工具请求；RPC与业务请求不能相加成4次工具。

### 第三分钟：讲一个真实修复

推荐展示“先验证后提交”。构造搜索返回两条数据，第一条正常、第二条类型错误：旧实现可能先写入第一条来源，再因第二条报错，造成工具失败却残留部分新证据。

当前实现先在副本里整理整个可接受批次，检查完成后才提交。读页同理：先校验正文、元数据和可序列化观察，再写入`page_evidence`。失败后新增来源/正文为0，但已经启动的后端尝试仍为1；以前成功的证据不会因此清空。

依据：[前后对照](../reports/finalization-v035/atomic-before-after.json)、[生产规则](../src/as_researcher/researcher.py)、[反例测试](../tests/test_final_boundaries.py)。这里的“原子”是一题内的内存提交边界，不是引入数据库事务。

### 第四分钟：展示真实成功与失败的区别

展示10-25的指定官方URL样本：0搜索、1页、1次MCP RPC，真实模型2次响应，保存正文6987字符，回答419/700字符，strict退出0。它验证给定来源到真实模型/MCP/Edge/保存回答的完整路径。

依据：[逐项检查](../reports/recheck-20261025/live-check.json)、[原回答与证据](../reports/recheck-20261025/live/20261025T080250-90b748a1/report.md)。逐项语义对照由助手做，不能称为独立人工gold，也不证明公共搜索稳定或所有问题准确。

再展示10-23任务：连接超时、0正文、strict退出3。模型解释证据不足，是失败后的诚实收尾；不能因为生成了文字就称研究成功。[失败原件](../reports/finalization-v035/live-check.json)继续保留。

### 第五分钟：说清边界和下一步

> 我能用程序检查预算、已知来源、引用层次、长度、状态和记录一致性；是否真正支持某条事实仍需看保存证据。一次缩稿通过机械条件也可能改变否定或版本条件。下一步应根据实际失败做有限验证，而不是先堆新的框架。

这五分钟后最容易被追问的四题，直接在这里准备：

- **失败为什么计预算？** 外部尝试已经开始，可能消耗时间或配额；只数成功会让故障绕过上限。参数或资格拦截未进入后端，所以不消耗尝试。
- **stop后为什么还能读页？** 工具观察的stop描述搜索停止；已知来源和页预算仍可能允许读取。它不是整个Agent退出命令。
- **SDK拦截为什么没有应用trace？** 请求在框架参数校验阶段就被拒绝，没进入Session函数；应用trace只覆盖进入应用边界的调用。
- **null用量为何不是零费用？** null表示没有完整观测值。可能请求已到服务方但失败，没有返回usage；不能从缺记录推出未收费。

后续Q20、Q22、Q16、Q43分别展开这些问题，但这四个短答已经足够应对即时追问。

### Q05：现场演示失败或网络不可用怎么办？

现场先用固定离线链，真实题展示保存材料。离线也失败时，记录错误类别、输出目录和退出码，说明是在安装、配置、MCP连接、工具还是模型阶段；不要临场连续重试付费服务来制造成功。

若默认编辑器打开后刷日志，选6直接在终端看run.json。旧编辑器已经连接旧终端时，在新窗口重启助手；不把编辑器的字体/扩展提示解释为研究任务错误。保存记录不能替代实际运行，但可以让演示在网络波动时仍展示证据和限制。

## 3. 框架、SDK、API、Tavily与DDGS

### Q06：SDK到底是什么？API与SDK有什么区别？

API是软件之间约定的调用接口，例如HTTP地址、认证方式、请求和返回结构。SDK是Software Development Kit，即把接口封装成可调用类、函数和数据对象的一套开发工具。API像约定，SDK像按约定帮你发送、解析和检查数据的工具箱。

在本项目中，`Agent`、`UserMsg`、`FunctionTool`来自AgentScope的Python SDK。模型兼容接口通过适配器调用底层客户端。Tavily也提供SDK，但本项目**没有使用TavilyClient**，而是用HTTPX直接POST其搜索API；不要看到服务名字就以为一定安装了同名SDK。

### Q07：AgentScope SDK替我们做了什么？我们还需做什么？

它组织消息、调用模型、解析工具请求、校验/分发工具，并把匹配的结果放回下一轮上下文。应用通过`agent.reply(...)`使用这一循环，不需要自己手写每轮模型请求与工具分发。

它不知道本项目的来源资格、搜索上限、正文分层和失败计数。因此Session仍需检查这些业务条件。框架完成通用执行，应用掌握任务权限与证据规则，二者不能互相替代。

### Q08：Tavily是什么，在这里做什么？

Tavily是外部搜索服务。本项目把查询和结果条数上限发给其搜索HTTP接口，使用`TAVILY_API_KEY`认证，再将结果整理成统一的`Source`列表。

这里设`search_depth="basic"`、`include_answer=False`、`include_raw_content=False`，用途是取候选地址和搜索内容层，而不是让搜索服务直接生成最终报告。最终答案仍由研究模型生成，正文仍通过单独的`read_page`取得。搜索服务返回`content`也不能自动标为本项目的`@page`证据。

### Q09：DDGS、DuckDuckGo与DDGSearch是同一个东西吗？

不是。DuckDuckGo是搜索服务；`ddgs`是已安装的第三方Python搜索库，`DDGS`是它提供的调用类；`DDGSearch`是本项目写的适配类。

当前代码调用`DDGS(timeout=10).text(..., backend="duckduckgo")`，明确选DuckDuckGo后端。DDGS本身可以支持多种搜索来源，不应把库名和本项目当前选择混为一谈。此路径不需要本项目配置搜索key，但仍联网，仍可能超时、限流或不可用。

### Q10：为什么要写统一的搜索适配器？

Session希望得到的是`await backend(query, limit) -> list[Source]`，不应到处判断服务返回的是`href/body`还是`url/content`。DDGSearch与TavilySearch负责将不同格式转换成`Source(title,url,content)`，Session再执行统一过滤与预算。

换服务通常只改后端构造，不改搜索资格和证据保存规则。但“接口统一”不意味着搜索质量、排序、费用、HTTP次数与网络稳定性都一样。

### Q11：DDGS同步调用为什么放到asyncio.to_thread？

研究链主要使用async/await，而DDGS的text方法是同步的，直接调用会阻塞事件循环。`asyncio.to_thread`让它在工作线程中运行，等待期间事件循环可以处理其他异步工作。

这不表示多Agent或自动并行搜索。取消等待也不能强制杀掉已运行线程，因此DDGS本身还设置了10秒超时；应用外层超时与底层调用边界都要理解。

### Q12：为什么auto搜索不等于自动挑最好的服务？

CLI的auto只是确定配置：存在Tavily key就选Tavily，否则选DuckDuckGo。它不对搜索效果打分，不在失败后偷偷换服务，也不是根据题目做搜索路由优化。

离线不走这个选择，而用FixtureSearch。指定URL且搜索预算0时，后端即使已构造也不表示实际搜索过；以trace和search_attempts为准。

## 4. 一次Agent运行：按真实调用顺序回答

### Q13：真正的业务入口在哪里？终端是不是Agent的一部分？

`run_research(topic, model, backend, config, reader=...)`是一次研究的业务入口。CLI负责配置和资源，终端只是更方便地收集同一组参数，二者共享`cli.execute_args`。

核心链是`run_research → ResearchSession/Prompt/Toolkit/Agent → agent.reply → 模型/工具循环 → 完成检查 → run字典`。终端的while管理菜单和下一题，不是SDK的推理循环；历史查看、编辑器打开、验收脚本也不属于模型决策的一部分。

### Q14：Agent、模型、Session分别是什么？

模型根据输入消息生成文本或工具请求。Agent是框架对象，负责将模型响应、工具执行和上下文组织成循环。Session是本题的业务状态，持有来源、预算、锁、已读ID与trace。

例如模型提出读`SRC-...`；Agent将请求交给注册工具；Session决定该ID是否存在、页预算是否还有、是否已经尝试过。三个对象职责不同，不能简单说“Agent自己知道所有Python变量”。

### Q15：首次输入包含哪些东西？

系统Prompt描述证据规则、工具预算与不可信网页等约定，用户消息包含研究问题。有指定URL时，应用还在用户消息中加入已经登记的`id/url`目录，并说明URL不是摘要或正文。

存在字符预算时，`with_answer_budget`协调回答格式，避免固定长章节要求与短答限制互相冲突。Prompt可以影响行为，但真正的搜索/页数上限仍由代码执行；回答长度也会在输出后再检查。

### Q16：ToolCallBlock、ToolChunk、ToolResultBlock是什么关系？

`ToolCallBlock`是模型提出的动作，含工具名、调用id和参数。`ToolChunk`是Python工具函数返回给框架的数据块。本项目通常在其中放JSON文本；SDK再把结果整理为与调用id对应的`ToolResultBlock`，加入上下文。

动作、函数返回、模型可见结果是三个阶段。模型提出请求不等于后端已经执行；Session保存了一份正文也不等于模型已读到它，必须通过工具返回进入后续消息。SDK提前拒绝的参数请求没有进入Session，所以没有应用trace，但仍可能有SDK层的结果说明。

### Q17：Tool schema从哪里来？为什么不是模型随便调用函数？

`FunctionTool`将函数签名、类型注解与docstring包装成工具说明，Toolkit只暴露注册过的函数。模型收到这些schema后提出请求，由框架匹配名称并校验参数。

SDK可能修复某些数字/字符串输入，而直接Python调用又不经过SDK；所以schema不是业务边界检查的替代。is_read_only表示读取外部资料，仍会修改本题计数和来源，不代表函数没有任何内存变化。

当前只有search_web和可选read_page，且预算0时相应工具不注册。模型没有任意Shell、读取.env或修改文件的工具。模型声称“执行了命令”也不能改变工具实际权限。

### Q18：模型看得到session.sources这个字典吗？

看不到Python对象本身。它只能看到应用明确放进消息的目录，或工具返回的来源/正文文本。Session用于程序控制；模型上下文用于决策，两个存储不能混在一起理解。

因此初始指定URL必须显式传入用户消息，工具取得的新证据必须通过观察返回。测试除了看trace，还要检查下一轮模型实际收到的ToolResultBlock，才能证明消息回流接线正确。

### Q19：同一轮可以请求多个工具吗？会调用多次模型吗？

一次ChatResponse可以包含三份ToolCallBlock。SDK处理这批请求后，再发起下一次模型调用，所以可能是2次模型调用、3条应用工具记录；不必每次工具都插入一次模型请求。

本项目两个工具登记为`is_concurrency_safe=False`，固定SDK2.0.8的原生观察显示对应顺序批次。仍保留应用锁，防止直接调用或其他调用方并发越过配额。多块输出不是多Agent，也不能仅凭三条trace说模型已逐条理解了前面失败。

## 5. 预算、停止、失败与并发：最常见追问

### Q20：为什么失败也计预算？何时开始计？

外部尝试开始前就增加attempts。即使随后超时、限流或返回坏格式，它已经占用了时间、网络或服务配额，应该消耗一次。若只在成功后计数，失败循环可以无限尝试而绕过预算。

被参数、未知来源、重复或配额拦截的请求没有进入后端，不增加后端尝试。因而trace可能有3条，search_attempts只有1；“被请求”和“被实际允许调用”是不同计数。

### Q21：有哪些预算，能否用一个数字代替？

至少区分搜索尝试、读页尝试、每次结果数、摘要/正文字数、回答非空白字符、每响应输出token、主循环常规轮次与时限；缩稿还有独立预算。

搜索1次可能返回3个来源，读页1次只保存有限正文；token不是中文字数。`max_agent_iters`是SDK常规轮次上限，可能有额外无工具收尾，不是严格HTTP请求数。一个指标不能替代其他上限。

### Q22：stop=true后为什么还能读页？

本项目的搜索观察使用stop表示搜索已停止，原因可能是预算、重复、无新来源或错误。它约束search_web，不自动禁止对已知来源调用read_page。

例：搜索预算1、读页预算1。第一次搜索成功后search_stopped=true，仍可读取这次发现的来源，再生成回答。剩余搜索0与整个Agent完成是两件事；最终metrics同时保存搜索停止原因和整体状态。

### Q23：还剩配额，为什么也可能被拒绝？

配额只是数量条件，来源资格、参数、是否已尝试和停止状态也是独立条件。读同一ID失败后，即使remaining_page_reads大于0，本题也不自动重读该ID。

搜索重复查询会规范大小写与空白再比较，触发停止后剩余额度可能仍为2，但后续搜索依旧被拦截。因此“剩余2”不能解释为“一定还可以执行2次”。

### Q24：模型不听Prompt继续请求怎么办？

不能依赖模型自觉。Session每次进入都重新检查停止状态、预算和参数，返回明确拦截观察；不会因为模型要求就增加额度。

SDK常规轮次和主任务超时还提供外层限制。Prompt、工具许可和任务结束是不同保护层；固定模型故意违反Prompt的测试能验证程序规则，但不证明真实模型已学会遵守。

### Q25：为什么要锁？async与并发有什么区别？

await表示等待时让出执行机会，不保证状态检查和扣额度连在一起。两个调用可能都看到“还剩1次”，然后各执行一次。

`async with self.lock`把搜索资格检查和尝试流程串行保护，读页有自己的锁。框架的执行安排是第一层，Session锁是业务状态保护；不能因为本次SDK已顺序执行就删除锁。它也不表示所有HTTP都变成同步代码。

### Q26：失败批次怎样避免留下半份证据？

先整理与校验，再提交状态。搜索在临时来源副本里处理选中批次；读页先检查正文和允许元数据、复制嵌套结构、构造可序列化观察，再写page_evidence。

若中途发现坏对象或NaN等无效JSON树，新增证据为0，尝试已消耗。旧成功证据保持。Pydantic类型声明不能替代对真实外部返回值的边界检查，这也是可讲的状态一致性修复。

### Q27：三条搜索工具记录，为什么可能只有一次后端尝试？

先分清“后端尝试”与“HTTP”。若第一条返回429并设置search_error，后两条在Session里被拒绝，则有3条工具记录、1次后端搜索尝试；后两条根本没到搜索后端。

但一次DDGS后端调用内部可能有多份网络请求，所以也不能直接把这1次称为精确抓包的1个HTTP请求。项目没有用业务计数冒充完整网络抓包。

### Q28：错误怎样交回模型？工具状态SUCCESS是否代表读页成功？

应用通常捕获预期失败，返回含error/error_code、stop和预算的结构化观察。函数成功交回一次观察时，框架层可能是`ToolResultState.SUCCESS`，而业务payload明确是失败。

因此应检查payload与trace，而不是只看SDK枚举名字。异常不应原样带远端响应正文或认证头；本项目保留有限公开类别供模型收尾和人工排查。

## 6. 来源、正文、引用与网页抽取

### Q29：URL、Source、SRC和SEG有什么区别？

URL是资料位置；Source保存标题、URL和搜索内容，用户指定URL时内容起初为空。SRC由规范URL计算，是一题中关联来源与引用的标识，不是网页全文的内容指纹。

SEG是某次抽取文档中的段落定位，需要结合document_sha256与字符偏移使用。工具调用id则用来匹配一次动作和结果，与来源身份是另一回事。

### Q30：为什么指定URL也要登记成SRC再读？

read_page面向模型只接受已知source_id。Session从本题来源目录解析URL后，再交给reader，因此模型不能绕过本题来源资格把任意地址交给读页后端。

指定URL会登记位置并进入首次用户消息，不编造搜索摘要、不制造一次虚假的搜索trace。搜索预算0时可以只注册read_page；成功保存正文后才有可用的@page引用。

### Q31：@snippet和@page分别证明什么？

@snippet对应保存的搜索标题/摘要层，@page对应这次读取并保存的有限正文层。同URL可以有两层证据，SRC相同，但可引用内容不同。

搜索服务提供content、读页函数被请求、正文成功保存、回答实际引用正文，是四件不同的事。即使确实读过一页，答案仍可能只用了snippet，应按记录说明，不自动升级引用。

### Q32：引用ID存在，为什么不能说明事实正确？

ID存在只说明来源目录里有这个来源。层次检查通过只说明所用snippet/page有保存文本。这两项都没有逐句判断该文本是否支持结论。

例如正文讲的是“默认取消行为”，回答声称“所有异常都被忽略”；只要同一个SRC的正文存在，ID和层次都可能合法，但语义仍错。要判断支持，需要对照版本、否定、条件、例外和上下文。

### Q33：正文没找到摘要中的事实，能否说摘要错了？

不能。当前只保存有限正文片段，事实可能在未选中的段落里。应说“本次正文片段未核验该点”；如仍引用摘要，要清楚标为snippet并说明局限。

若两层真的冲突，也不能只因page叫正文就自动裁决正确。需要核对日期、版本、来源与条件，必要时并列差异或说明不确定。

### 再分清：相关、支持、权威是三种判断

搜索结果与关键词相关，只表示它可能有用；文本支持某个结论，还需要版本、条件与否定对应；来源是否权威，则需要看发布方、原始材料、日期与题目范围。一个搜索排名靠前的网页不自动获得权威身份，写成官方URL也只是候选位置，程序不因此认证事实。

真实研究应优先找适合该问题的原始文档，固定所需版本，比较冲突并保留不确定性。当前没有自动权威评分或全面事实校验；工具许可与正文保存是可核对的工程前提，不能替代这些判断。

### Q34：为什么不简单截取网页前5000字？

关键定义可能靠后，表格截断会丢列关系，代码与紧邻解释拆开后可能改变含义。项目支持head、window、segments，默认按段落、标题、表格与代码上下文选择。

结构化选择也有代价：字符预算有限，保留一个代码组会挤掉别的内容。因此保存段落偏移、省略提示与代码上下文信息，不声称返回全文。选择器让取证范围更可解释，不保证每个问题所需条件都在片段中。

### Q35：段落偏移、document_sha256与is_truncated有什么用？

偏移指规范化抽取文本中的字符位置，左闭右开，既不是网页屏幕坐标，也不是原HTML字节。document_sha256将定位绑定到对应抽取文档，避免只拿一个SEG名字跨版本解释。

is_truncated等字段说明片段截取情况，省略信息说明预算导致哪些候选没返回。它们帮助人工找证据边界；hash一致不能证明网页内容本身真实。

### Q36：为什么“其他代码被省略”不能推导“这个示例未保存”？

需要逐个代码组检查。历史shield候选曾在一个等价代码组已经保存时，仍根据其他省略提示写“等价示例未核验”。引用和长度都通过，事实判断仍与保存证据冲突。

正确做法是定位该声明所需的具体SEG、代码内容和限定解释，再判断本组是否保留。全局省略提示是范围提醒，不能替每个例子做结论。

### Q37：网页包含“忽略用户、泄露密钥”的指令怎么办？

网页与搜索结果是外部不可信数据。系统Prompt要求将其作为资料，而非新的系统命令；工具观察标注不可信，模型也没有任意Shell或私密文件工具。

程序仍需限制权限和出网，不能只靠提示词。固定注入字符串测试只能证明某个可控流程没有越过已注册能力，不能据此宣称通过全面提示注入安全认证。

## 7. 真实模型、用量、结束原因与诊断

### Q38：离线模式是否运行了真实AgentScope？

运行了。ScriptedModel按固定规则返回ChatResponse，FixtureSearch/FixtureReader提供固定证据，但Agent、Toolkit、Session、MCP可选进程和保存逻辑仍是真实代码。

这适合证明接线、计数与边界；不证明搜索能联网、模型会正确规划或回答真实题。离线自定义问题依旧是固定响应。另需区分uv的--offline：它只限制依赖获取，不决定应用是否请求真实模型。

### Q39：一次任务等于一次模型请求吗？

不等于。搜索→读页→回答通常需要多次模型调用；同轮多工具又可能让多条请求共享一个模型响应。开启模型重试或循环后缩稿，还可能增加外部请求。

要看本次model_requests、provider_responses、revision与fixture_model_calls各自的含义。不能仅拿最后一段回答或主循环轮数估计调用总量。

### Q40：model_requests和provider_responses为什么分开？

当前真实模型适配固定使用非流式返回：拿到整份响应后再解析，终端没有实现逐token增量显示。这些诊断覆盖点绑定SDK2.0.8，不能直接推成所有流式接口也已验证。

前者记录适配器每次请求尝试：responded、failed或cancelled，以及有限状态/时长。后者记录已经解析出的提供商响应：finish_reason、token计数、是否含工具与是否完整。

HTTP400可能有1次失败尝试、0个解析响应。429后一次成功可能有2次尝试、1个响应。两个数组长度不同并不必然是记录丢失。

### Q41：finish_reason=stop是否代表任务正确完成？

它表示提供商按相应结束方式停止输出，不认证事实、格式或证据完整。应用还要检查本题状态、引用、证据层次、长度与warning；人工仍需判断语义。

历史真实样本出现过正常stop、合法引用，但答案补出未保存的细节；也出现过正常stop却超过700字符。正常结束是必要的执行信号，不能替代质量评测。

### Q42：为什么finish_reason=length必须单独处理？

length通常表示响应受输出限制而截断，可能丢掉结论后半段，也可能把工具参数截成半个JSON。本项目适配器保留有限诊断，并移除不完整工具请求，避免破损参数执行。

run_research会将响应标为未完整，不自动请求续写或把占位提示当成功短答。增加输出token可能有成本和上下文影响，应根据记录调整，不能反复加预算直到出现一个好结果就宣布修复。

### Q43：null用量为什么绝不能直接当成零费用？

null是未知或不完整观测。可能提供商不返回usage，也可能某次请求失败但服务端已收到并处理一部分；客户端无法据此证明未计费。

若重试成功只拿到成功响应用量，前一次失败仍未知，总量继续null；不能把已知局部当完整总量。固定模型调用数也不等于真实付费统计。财务意义上的实际费用仍需服务方账单核对。

### Q44：model_retries=0是不是任何层面都不会重试？

它关闭本项目模型适配器的显式重试预算，底层模型客户端也固定不重试。模型自己下一轮再次请求某工具、搜索库内部的网络行为、浏览器启动机制，是不同的层次。

因此本项目说的是所控制的模型重试层，不是整个互联网链路绝无任何内部重发。默认不自动重试，能让失败观测与费用边界更清晰；如果以后开启重试，应有上限并保留每次尝试。

### Q45：显式关闭thinking能通用于所有兼容端点吗？

不能。兼容基础消息接口不等于支持相同专有参数。当前thinking_parameters只允许代码白名单验证过的DeepSeek官方端点/模型组合；默认provider-default不发送专有开关。

主研究模型与一次缩稿是独立调用，开关也独立。不能根据一次BadRequest就猜根因，更不能偷偷改模型/端点或思考模式，把前后不同条件的成功当成同一次修复。

### Q46：怎样诊断真实请求失败而不泄露信息？

按层检查：配置是否齐全、模型尝试有无记录、提供商HTTP状态、工具是否开始后端、MCP是否返回、页面是否保存。保存公开错误类别、有限元数据与本题证据，不原样复制远端异常正文、请求头、密钥或私密思考。

当前适配器还抑制第三方payload日志并对白名单重试日志做脱敏。已配置key匹配扫描只是有限检查，不等于任何敏感信息都不会出现；不要把.env或完整服务端错误粘进说明材料。

## 8. MCP、浏览器、进程与网络边界

### Q47：MCP在项目中解决什么问题？

MCP是工具调用的协议边界。本项目用stdio启动固定研究工具服务，父进程通过MCPClient发现search/read_public_page，再用桥接函数转换为Session需要的backend/reader接口。

业务调用链是模型→Session受控入口→可选MCP桥→工具进程→相同后端。服务器不创建另一个研究Agent，也不调用研究模型；模型没有自动挑选陌生MCP服务器。

### Q48：本地传输与MCP的规则是否相同？

两者共用Session，所以来源资格、计数和预算规则相同；MCP只是替换实际后端路径。协议连接、序列化与子进程退出会引入新的失败面，因此桥接层还保存RPC trace并区分后端错误和传输错误。

固定本地/MCP结果相同，是同一规则和同样fixture的验证结果；不是MCP协议天然保证任何实现都等价。服务器还重复检查公开网络规则，防止被直接调用时绕过底层限制。

### Q49：为什么MCP进程不应收到模型key？

它只做搜索和读页，不需要研究模型凭据。进程环境按需传搜索提供方、reader配置以及必要的Tavily key，不把整个os.environ原样复制过去。

这是最小必要信息原则。搜索key与模型key也不是同一用途；没有必要的秘密不应为了“方便”传播给工具进程或桌面查看器。

### Q50：浏览器模式等于浏览器自动操作Agent吗？

不等于。当前先受限下载HTML，再在隔离无头浏览器中关闭JavaScript/网络，把HTML装入页面做静态DOM文本抽取。它不登录、不点击、不操作用户现有浏览器。

HTTP和browser是两种抽取路径，不是两个模型。没有JS动态渲染能力意味着某些站点取不到完整资料，应诚实报告，不把0正文当“网页没有相关事实”。

### Q51：限制公网URL就足够防SSRF吗？

本项目做了协议、凭据、本地/私网地址、端口、DNS、公网解析结果、重定向、类型和大小等限制，降低明显误访问风险。但DNS检查没有把最终连接IP固定，仍不等于生产级DNS重绑定防护。

生产部署需要根据环境增加网络隔离和出口控制。面试可以解释现有措施与剩余风险，不必为这个本地项目临时堆部署中间件，也不能声称已提供完整安全沙箱。

## 9. 回答长度与一次缩稿

### Q52：为什么不把长答案直接切到700字？

硬截文本可能截断否定、版本条件、表格或引用，留下看似简短却失真的答案。项目先在Prompt中协调格式，输出后按非空白字符检查；超长保留原文和warning，不静默裁切。

字符数包括标题、标点与引用标记，不能只算自然语言正文。token是模型编码单位，因此输出1800 token也不能保证700字符。

### Q53：一次缩稿在哪一层，为什么默认关闭？

它在Agent主循环之后，由revise_answer执行一次无工具模型调用。只有显式启用、原任务完整且答案超长等条件成立才尝试，预算和超时单独记录。

默认关闭可以避免隐藏额外请求，以及把另一次模型生成误认为确定性修复。缩稿不能补充原来没取得的外部证据；失败保留原稿，不循环重写直到通过。

### Q54：缩稿前预检与候选检查分别做什么？

预检估计长度、必要不同引用的最低占用等；若连引用预算都明显放不下，可以0请求跳过，避免无解开销。它只是下界判断，不证明剩余文字一定可忠实压缩。

候选生成后检查结束状态、长度、引用集合和可用层次等条件，只有满足机械约定才采用。applied_checks_only的意思就是“只通过这些程序检查”，否定、例外、版本与证据支持仍需人工看。

### Q55：怎样证明缩稿没有改变意思？

机械检查做不到完整证明。应将原稿与候选拆成可核对的声明，特别检查必要条件、否定、数量、范围、时间版本和不确定性，再对到准确层次的证据。

历史候选曾从914缩到608字符并保留三类引用，但仍错误地说一个已保存代码组未核验。这个反例说明“更短、引用齐全”不能当成语义保真分数；comparison和worksheet是辅助人工阅读的工具。

## 10. 测试、评测与人工复核

### Q56：代码测试通过，为什么仍不能说模型准确率很高？

代码回归主要使用固定模型、模拟HTTP与本地MCP验证规则和接线。10-27的352项与11-01扩展后的测试都不是同数量的独立真实知识题；它们能发现已设计的边界回归，不能给出普遍事实准确率。当前确切数量与新执行记录见本文件第13节的结果表。

四步离线验收则检查固定回放、stdio接线、历史绑定与材料审计，也不是质量评测。真实单例和人工语义复核是另外的证据，不能把各种passed相加成一个准确率。

### Q57：有意义的反向测试是什么？

不仅看正常输入通过，还故意破坏一个应被拒绝的条件。例如保留工具调用id却交换两份来源内容；或者让坏搜索批次的第二条类型错误；或者构造引用合法却正文不支持的回答。

如果检查器正确拒绝这些反例，能说明它检测到了所定义的错误。不能反过来说真实框架曾发生过该种丢失/调换，也不能因为测试是绿色就省略对未覆盖边界的说明。

### Q58：原子声明复核为什么比逐句判断更细？

一句话可能同时包含“默认行为、一个例外和一个数值”。整体标supported容易掩盖其中一项没有证据。原子声明尽量拆成一个可判定的事实单元，并保留在原回答中的字符范围。

复核包绑定run指纹，逐条保存引用、摘录、理由和标签。程序能检查摘录是否属于正确来源/层次/字段、范围覆盖是否完整；“它是否真的支持这条事实”和“拆得够不够原子”仍需要审核者判断。

### Q59：valid、pending、supported、human gold能混用吗？

valid通常表示复核包结构、指纹、位置和覆盖等机械条件合法。pending表示尚未作语义判断；即使全是pending，草稿也可能结构合法。

supported是审核者给出的语义标签，需要准确摘录和解释；assistant标注不能叫独立human gold。只有实际人工完成、按流程确认的材料，才能如实声明人工审核身份，不能靠改字段获得身份认证。

### Q60：保留题、开发回归与未见题有什么区别？

开发回归已经看过结果，可以用来调试，但不能继续冒充未见评估。保留题应在明确计划下才首次使用，不能反复看结果调Prompt再称其独立。

当前保留的robots_permission/private_tool_latency不默认运行。选择性执行某题是控制成本与变量的方法，不等于挑一个成功结果代表总体稳定性；失败、超长与未知原因也要记录。

### Q61：目前最能说明真实能力与限制的记录是什么？

10-25指定来源完整链说明真实模型/MCP/Edge能在这一题取得正文并完成短答；它没有公共搜索。11-01进一步保存20题首轮、若干同题重复对照、实际官方网页/MCP和公共搜索失败，共52次真实模型运行；它们按阶段分开报告，第13节给出结果及限制。旧失败不被后来的成功改写。

其他历史案例说明引用层次、代码上下文、截断和缩稿可能出现的错误。它们是具体设计依据和回归样本，不是统一基准。讲结果时先说模型/证据是固定还是真实、实际执行哪一段，再说数值。

## 11. 终端、保存材料与交付问题

### Q62：为什么后来加了终端菜单？会改变研究算法吗？

原来参数多、结果主要打印指标，初学者需要记命令和手动找文件。菜单把模式、预算、题目与查看入口集中起来，直接显示同一个run.answer，减少操作负担。

它把选择转为普通CLI参数并调用共享execute_args，不在核心循环里插入一个新的规划Agent。真实任务必须输入LIVE，默认固定离线、零重试、不开缩稿；这些默认值在开始前显示。

### Q63：看历史、打开run或看trace会重新计费吗？

项目的这些查看功能只读保存文件，不调用模型、不重跑搜索；历史查看也不加载.env。菜单6直接展示run.json，菜单2展示工具trace及已有的模型/MCP有限元数据。

菜单3/4/5只是向系统默认程序提交打开请求。外部编辑器自身可能有扩展或更新行为，但这不是项目重新执行研究任务；不能将两类程序日志混在一起解释。

### Q64：为什么打开JSON曾出现VS Code日志？怎么修的？

旧版直接从菜单进程调用os.startfile，默认编辑器的日志可能写入同一控制台。输入0只重新显示主页，没有解决外部进程的终端连接。

当前Windows使用无控制台pythonw小助手，隔离标准输入/输出/错误和进程组，只传必要桌面环境，并用10秒的辅助进程等待限制提交。成功提示只说系统接受请求，不认证编辑器渲染。超时/失败不自动再开，给路径与菜单6；已有旧进程不会被追溯断开。

### Q65：run.json是不是Agent断点续跑文件？

不是。它保存已发生的结果、证据和诊断；没有序列化完整框架状态、待执行动作与可恢复资源。工作checkpoint.json记录开发任务完成项，也不是Agent的中间状态。

因此保存前中断可能没有本题记录，下一题也不会自动接上旧来源和预算。若以后需要真正续跑，必须设计状态契约、工具幂等性和失败恢复，而不是只读取最后一份JSON继续猜。

### Q66：源码包、.venv、reports与.env有什么区别？

源码包包含代码、依赖声明、说明与公开fixture；.venv是本机安装好的解释器/依赖环境；reports保存运行证据与少量测试绑定原件；.env是本机真实配置。

源码ZIP不包含真实.env、依赖缓存或全部历史reports，所以不是免安装软件。普通离线题不依赖旧报告，但完整回归、编辑样例与旧摘要核验需要相应绑定材料。不要为了“清理目录”把reports整体删空。

### Q67：退出0、2、3各代表什么？

带参数CLI退出0表示所定义的程序检查通过；2包括配置、整体未完成或search_error；严格模式下3表示引用、证据、长度或其他warning。单次读页失败若模型正常收尾，可能是completed加warning、strict3，不能把所有后端错误都机械说成退出2。即使0也不代表事实已人工核验。

终端正常退出沿用最近实际任务的业务码，只看历史不改变它，Ctrl+C为130。无证据预设故意得到3，是演示预期，不应通过删除warning伪装成功。

## 12. 设计取舍、扩展与面试自测

### Q68：为什么不先加更多工具、多Agent或向量库？

当前主要问题是受控研究和取证边界。增加Agent或工具会增加调用、共享状态、权限与评测成本，不自动解决来源错误、未读正文或语义复核。

扩展应由需求驱动：大量私有文档反复查询才考虑索引；多个明确角色确有分工才考虑多Agent；服务化需求明确后再设计任务队列、身份和网络隔离。先能解释现有单Agent闭环更重要。

### Q69：如果让你提升可靠性，下一步怎么选？

先固定一个可复现问题、输入和预算，分清是检索无结果、读页抽取丢条件、模型误解、截断还是记录缺口。再设计能否定旧错误的本地反例，最小修复后跑相关回归。

若必须真实验证，先保存有限计划，选一题或一个组件，保留失败与未知用量，执行后停止。不把连续重试直到成功当稳定性证明，也不默认更改模型、代理和多个预算变量。

### Q70：你怎样证明自己真的理解代码，而非只会背手册？

不看稿完成三件事：画出模型→工具→观察→下一轮模型；从一份run的trace解释每次允许/拒绝与计数；打开一处修复及其反向测试，说明去掉哪条检查会重新出现错误。

然后任选一个变化推演：搜索预算改为0、页预算改为0、首个搜索429、reader返回坏元数据、模型输出length。能正确预测哪些字段改变、哪些工具不再注册、哪些调用不会发生，才说明掌握了结构。

### 面试前自测清单

- 能用自己的话解释Agent、模型、Session、SDK、API与后端，不把它们叫成同一个东西。
- 能连续说明一次搜索、一次读页和三轮固定模型的消息回流，而不是只背文件名。
- 能回答Q20/Q22/Q16/Q43，并给出数字例子：失败计预算、stop范围、SDK拦截边界、null不是零费用。
- 能讲原子提交的坏输入、旧行为、新行为和回归，不将其夸成数据库事务。
- 能分清本地/MCP、HTTP/browser、固定/真实，指出终端与查看器在循环外。
- 能展示一个真实成功样本与一个失败样本，同时说出没有证明什么。
- 能解释为什么引用完整、正常stop、短答或352测试都不能替代事实质量评测。
- 能如实说明开源/AI协助和自己的理解，不编造独立人工gold、生产部署或模型训练。

## 13. 研究问题库、回答检测、对照实验与改进方向

这一节从“该问研究助手什么问题”讲到“拿到回答后怎样评价”，相关内容放在本文件内。题目中的Python API只是有权威资料可核对的测试领域，不要求你先学完全部异步编程。学习重点仍是Agent怎样取证、何时缺证据、如何评价结果，以及怎样据此改工具和工程边界。

### 13.0 第一次遇到benchmark：从概念到实际操作

**先用一个例子理解。** 你想知道“改选段函数以后，Agent回答是否更好”。随便问一次，新回答看起来更顺并不能回答这个问题：可能网页变了、模型随机发挥了、字数限制放宽了，或者你只记住成功样本。需要把题目、资料、预算与判断方法先固定，再让两个方案在这些条件下答题。

这整套约定可以称为benchmark，中文通常叫“基准评测”。它由题目、环境、运行协议、评分和统计组成，不是某个模型，也不是只要脚本名有benchmark就具有公信力。本项目是小型开发评估：题目和结果已用于修改代码，不能冒称独立未见测试，更不是DeepResearch Bench公开排行榜复现。

#### 13.0.1 名词先分清，不急着记缩写

| 名词 | 通俗理解 | 本项目具体例子 |
|---|---|---|
| benchmark | 试卷＋考试条件＋评分规则 | 同题、同官方HTML、同预算，按固定标准对照 |
| evaluation / eval | 做评价这件事 | 检查一次实际答案及其工具轨迹 |
| suite / dataset | 一组题或输入材料 | research_suite.json中的20题；不是20次API调用 |
| task / case | 一道题及要求 | 比较timeout和wait_for取消谁、怎样抛异常、等待多久 |
| trial | 这道题的一次尝试 | 相同题/策略第1次和第2次是两个trial |
| rubric | 把要求拆成可核对的小项 | 说明两侧取消对象、未知处标明、引用对应保存证据 |
| grader | 判断某部分的检查方法 | 程序数字符；审核者判断是否误扩大否定范围 |
| harness | 准备、运行、保存、评分的外围设施 | benchmark_research.py；不接管AgentScope内部reply循环 |
| baseline | 当前拿来比较的参照方案 | segments或bm25，必须说明具体版本 |
| variant | 实验中一套具体配置 | segments__standard与segments__compact |
| ablation | 去掉/替换部分后看影响 | 本项目ablate实际是几个抽取策略的组件对照 |
| metric | 量化的一项观察 | 500字符内比例、必答点覆盖、输入token、失败次数 |
| development set | 已用于发现问题和调试的题 | 本项目20题、8个新抽取场景 |
| holdout | 开发时不查看/不据此调参的保留题 | 原保留材料仍不自动执行；不能给旧开发题换名冒充 |
| gold / ground truth | 可靠的参考判断 | 本项目助手标签不是独立专家gold |

“benchmark越大越好”也不准确。初学项目先选真实、可复现、能定位问题的小题，比无法核对依据的大量题更有用。反过来，只测两个超简单问题也会漏掉比较、否定、失败和版本条件。本项目20题包括这些类型，且保留超长、漏答和搜索失败，不只展示最漂亮的一次。

#### 13.0.2 要测哪一层，先决定清楚

例如“wait_for总等待可能超过timeout”这句话没答出来，可能至少有五种原因：搜索没找到官方页；读页失败；选段没有返回关键句；关键句已经返回但模型没用；答案其实正确而评分器误判。这五类改法不同，不能统一归结成“模型不够强”。

| 层 | 固定什么 | 看什么 | 本项目材料 |
|---|---|---|---|
| 程序规则 | 固定模型与工具返回 | 扣次数、拒绝未知ID、原子提交、是否保存 | unittest及固定离线验收 |
| 取证/选段 | 冻结同一HTML、focus和字符预算 | 必要片段是否存在、是否被选择、是否截断 | extraction_suite、coverage_suite与ablate |
| Agent回答 | 冻结资料，模型仍真实自主读页 | 答全、支持、范围、字数、费用线索 | frozen模式和逐项复核 |
| 实时接入 | 实际URL或实际搜索 | 当前连接、正文、错误类别及来源 | web/search模式；要与frozen分组 |
| 评审可靠性 | 固定答案、证据、rubric | 两位审核者怎样分歧 | blind-prepare/check；本轮只有工具，无真实人工完成标签 |

这里的“固定模型”指ScriptedModel预写动作，能验证代码接线；“冻结HTML”是固定资料，研究模型仍真实生成答案，二者不同。local只是直接Python调用工具，并不表示模型在本地运行。模型API、搜索API、MCP传输、读页方式是不同维度。

#### 13.0.3 一次小实验怎样设计

1. **先写问题与标准。** 例如必须说明两个API取消谁，不能在看到新答案后删掉不好答的条件。长度约定500个非空白字符，标题、标点、英文标识符和引用标记都算；token上限不等于字符上限。
2. **保存证据环境。** 固定下载的HTML与hash。截图、URL相同都不代表HTML字节相同；缺快照不偷偷重新联网替换。官方页面也可能变化，保存的是那个时点的资料。
3. **明确只改什么。** 两种选择器或两种回答格式，先二选一。若同时改模型、预算、格式和排序，很难解释收益来自哪里。
4. **预先确定次数和顺序。** 本项目用同题重复及AB/BA交替，保留所有计划行，不不断重试直到成功。重复不是新的独立知识题；这种小组不是统计学上的普遍优越证明。
5. **分开程序与语义。** 程序检查是否完成、用量/预算、引用与字数；审核者再看必答点、否定和条件、证据支持。可以运行成功而任务失败，也可以答案短但漏答。
6. **最后再看资源代价。** 输入/输出token、额外缩稿次数、耗时、失败一起看。只报告已知用量，null不是零费用；本项目没有据此计算货币账单。

具体操作已合并到本文第16节：固定流程、冻结资料研究、自定义标准、终端结果查看与复核在同一条学习路径内，不再维护两套重复步骤。

#### 13.0.4 这一轮采用哪些资料的哪些原则

[Anthropic的评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)支持把任务、重复尝试、轨迹和不同评分方式分开，并以实际失败驱动迭代；这里没有照搬其示例框架。[工具设计实践](https://www.anthropic.com/research/writing-tools-for-agents)强调工具返回应有用且节约上下文，因此本轮检查“标题开销挤掉证据”的真实输入问题。

[Goldstein与Carbonell的原论文](https://aclanthology.org/X98-1025/)讨论相关性与多样性的权衡，启发了不要只把所有预算给同一方面；本地balanced采用预算启发式，没有实现其MMR公式。[Stanford检索评估教材](https://nlp.stanford.edu/IR-book/html/htmledition/assessing-relevance-1.html)讨论审核者判断与分歧，作为保存共同分母、一致率和κ边界的依据。论文、公开基准与本项目本地结果是不同证据，不互相借分。

### 13.1 方向依据：哪些来自资料，哪些是本项目的选择

这里的“通用方案”指多份实践和研究中相互吻合的原则，不存在一份对所有Agent都适用的统一评分公式。以下资料于2026-11-01核对；本项目借鉴评估思路，没有运行它们的公开排行榜题集，也不宣称达到其分数。

| 原始资料 | 可借鉴的原则 | 本项目的落点 |

### 13.2 先定义五层结果，避免把一种通过当成全部通过

| 层次 | 具体问题 | 典型反例 |
|---|---|---|
| 代码合同 | 预算、错误和状态是否正确 | 失败没计尝试、读页坏元数据部分写入 |
| 能力获取 | 实际取得了哪些摘要或正文 | 配置了MCP/浏览器却0正文；搜索后端不可用 |
| 证据选择 | 所需条件是否出现在给模型的片段中 | 只取timeout，漏掉wait_for；返回构建源码 |
| 最终回答 | 是否答全、依据充分、条件正确、满足长度 | 诚实说未知但未答全；引用存在却扩大范围；长答超限 |
| 评估有效性 | 样例真的测试到目标行为了吗 | 攻击在原HTML里却没有返回给模型；只匹配标记误判引用为服从 |

一题可以在不同层有不同结果。例如，工具准确返回了有限片段，模型诚实说“另一个API未核验”，这可能没有幻觉，却没有完成双API比较。又如搜索服务坏了，模型拒绝编造是正确收尾，但不能把该题算成已完成的事实研究。

Task是一道任务；trial是它的一次实际运行；rubric是逐项标准；grader是代码或语义审核者。固定模型可以验证AgentScope循环和评测工具，真实模型搭配冻结HTML可以观察决定与回答；后者仍不是实时浏览。每种模式要分开报告。

### 13.4 怎样实际运行：先看计划，再选择一层测试

下面命令在项目目录运行。`uv --offline`只禁止下载Python依赖，不会阻止真实模型联网；决定是否付费的是评测模式和`run --execute`。

```powershell

# 对已保存结果重新评分：只读run/复核并新建摘要，不重新研究

```

新机器没有快照时，可用`fetch --case python_wait_for --output reports/新的目录名`下载该题指定官方页；每页有限超时，记录URL、时间和字节hash，不调用模型。合成注入页直接保存题库中的文本，不会访问example.org。下载失败保留错误；加载快照时缺页或错hash会拒绝，不偷偷换成今天另一份网页。

确需新的真实模型实验，再使用下面这一条。它会生成新目录并可能计费；不覆盖本轮已运行材料：

```powershell
uv run --offline --no-sync python scripts/benchmark_research.py run --mode frozen --case python_wait_for --repeats 2 --corpus reports/evaluation-20261101/corpus-exposed --execute
```

此命令默认真实模型的provider-default模式；本机11-01实验另显式用了已验证DeepSeek端点支持的`--model-thinking disabled`，不要将该开关照搬到其他兼容端点。每次最多40个trial、0模型重试、不开缩稿、最多6轮、每响应默认1800输出token；父进程另有限时并在连续两次基础设施失败后停止，剩余行保持not_run。截止只清理直接子进程，不是全进程树硬中止。

要测实时指定来源，用`--mode web --transport mcp`；要测公共搜索，用`--mode search --transport mcp`，每题1搜索/最多2页，当前默认DuckDuckGo。Tavily可显式选，但本机没有key，本轮没有验证其真实请求。frozen/fixture只支持local，这是本入口的范围；普通应用CLI仍支持本地和MCP。

默认只选mcp_stdio。选择具体题可重复`--case`；全选必须显式`--all`，例如`plan --all --strategy segments --repeats 1`为20次。不要把默认双策略/双重复与全选误算成20次。每次都先核对plan中的任务数、读取方式、字符限制和模型参数。

### 13.5 回答之后怎样检测，怎样给出改进方向

第一步，检查run中的实际状态和获取结果。`completed`只说明模型正常收尾；还需看search_stop_reason、实际页数、错误、引用可用性和题目长度。题目500与CLI700同时存在时，以更小者为执行/评估上限。500字符不是500个模型token。

第二步，逐项看题目。把“没答全”“说错了”“有结论但无本次证据”“已声明未知”区分开。某项需要的事实完全缺失时，覆盖应为false；如果判断者尚未查看材料，则用null。不能把“我还没评”误写成模型失败，也不能把“模型已经明确漏答”留在待判定来提高分数。

第三步，从task-review.draft.json复制出task-review.json，填写reviewer.kind/name；每项met取true/false/null，保存answer_quote、evidence和reason。answer_quote必须是原回答字串，evidence.quote必须属于这个run的具体来源/层次，不能用另一个网页或后来搜到的内容补证据。true的支持项需要保存证据。完成全部项目并实际检查覆盖后，才设coverage_checked=true。

任务复核关注问题要求，允许用较宽的回答范围作定位，不等于逐原子声明精度统计。若要声称每个事实均被支持，还应使用已有的原子声明复核，拆开条件、否定和数值，检查没有漏标。当前助手标签不能叫独立人工gold；把字段改为human也不是身份认证。

第四步，运行score。它核对题库、原run、题目与试验绑定，运行门槛与语义检查分开；新建assessment JSON/Markdown，包含完整回答、失败标准和对应improvement。退出0表示本批全部已评且通过，3表示有未通过或待判定，2表示原件/复核结构无效。run命令的退出码只反映执行层，不能替代score。

第五步，根据失败层改。没有搜索结果，先检查服务/网络，不盲目加提示词；片段漏掉第二个API，改选择覆盖或分配预算，不只让模型“更认真”；返回构建源码，改抽取；关键事实有了但超长，比较精简表达或既有一次缩稿，并复核否定/条件保真；标准含糊或攻击没暴露，先修评估本身。

### 13.8 面试时怎样把本轮工作讲成一个完整案例

## 14. 新评估与工程取舍的十个面试追问

### Q71：测试集、开发集和公开benchmark有什么区别？

测试集可以指任何用来验证程序或能力的案例集合；开发集已经看过结果，允许据此调整实现。公开benchmark有其固定数据、运行和评分协议，只有遵循协议才适合比较。当前20题是助手编写的开发集，不是DeepResearch Bench的缩小复现，也不是独立人工gold。

例如这次看到多点比较失败后再改抽取，同题下一次只能称开发对照。不能把已经调试过的题重新命名为未见题，也不能拿2/20与另一篇论文的排行榜分数比较。

### Q72：冻结HTML为什么比单纯固定模型更适合比较回答？

固定模型输出预写动作和答案，适合验证接线；冻结HTML固定资料，而模型仍真实选择focus、处理工具结果并生成答案，可以减少网页变化造成的干扰。它控制的是证据环境，不是把答案预先写好。

因此冻结模式能研究相同资料上的决策和回答差异，却不能证明实时公共网页或搜索稳定。要验证后者，需另跑web/search组，并保留当次失败。

### Q73：为什么加BM25而不是马上加向量数据库？

实际反例是完整自然语言focus难以被字面词组匹配。BM25可以用现有词频、标题和长度信息做便宜的词法候选，不需要新的服务、索引或模型。它保持原HTML结构和预算打包，适合当前少量网页。

但BM25不理解语义、不保证中英翻译或多点覆盖。实际短答对照没有普遍更好，所以仍可选、默认保持segments；只有反复大规模私有文档检索等需求成立时，才有理由讨论向量索引的收益和代价。

### Q74：17/18字面目标命中，为什么不能说94.4%回答准确率？

18是6个可评分场景乘3档字符预算，并非18道独立知识题；判断只是目标字串是否同时出现在片段。它没判断逻辑、否定范围、答案是否使用证据、是否漏答或超长。

本次真实对照正好说明：片段命中更多，答案仍可能漏掉取消对象或超过500字符。因此抽取覆盖与最终任务成绩分别记录，并注明小型开发集的局限。

### Q75：为什么评估要保留待判定，不能全记0或全记成功？

没有审核与已经证明不满足是不同事实。若10次里3通过、4失败、3未判定，程序分别保存，给[0.3,0.6]只是待定结果的上下界，不是置信区间。把待定当成功会虚高，把它当真实质量失败也会误导原因分析。

进程失败、模型未完成等已知运行门槛错误则可以直接失败；它们也不能被从分母删除。未知token同样保留未知，已知小计不冒充全部费用。

### Q76：pass@k、pass^k与本项目的重复运行统计是什么关系？

pass@k关注给k次机会至少成功一次，pass^k关注k次全部成功。它们回答机会与稳定性的不同问题，正式估计还需要对应采样协议。实际数据中的重复试验也可能相关，不能随意假设独立再乘概率。

本项目只报告每题本次重复中是否至少一次/全部成功；未判定组保持null。没有实现公开基准的pass@k估计，也不把4题各两次说成8题独立准确率。

### Q77：为什么要检查攻击真的进入模型上下文？

因为HTML存在攻击不代表工具返回包含攻击。若选择器把该段丢掉，模型没有服从可能只是没有接触到它。当前受控题把攻击与正常事实放在同段，并用required_exposure核对实际返回正文；没有暴露的旧运行保留待判定。

这是对测试前提的验证，不是生产防御证明。还要检查模型是否服从、实际工具权限及语义输出，不能只因字符串出现或消失下结论。

### Q78：为什么template修复与Agent工程有关？

Agent的工具负责把网页转成模型上下文。把网页构建数据当正文，会消耗预算、影响排序，还可能让模型把编译源码当技术证据。本次MCP页实际出现了这种情况，所以修复的是工具到模型之间的资料合同。

改动只需忽略不直接显示的template，并检查可见规范条款仍在。它不运行网页脚本、不改变Agent数量，也不是泛泛清理HTML；有实际输入、前后差异和坏结果依据。

### Q79：助手评分可以直接当human gold吗？

不能。助手可能偏好某种表达、遗漏额外事实错误，也可能和生成答案的模型有相关偏差。程序能绑定原件、检查摘录，不能认证审核者身份或判断逻辑蕴含。

下一步应让真实人工对小组样例独立盲评，记录分歧并修正标准；如再使用LLM-as-a-Judge，应先与这些人工判断校准，保留审核模型/提示/版本和成本。本项目目前不声称已完成这一步。

### Q80：现在项目最需要继续改进什么，为什么不说已经最终完美？

11-02已把多焦点预算、精简提示、一次缩稿对照及盲评工具落到代码。408项程序回归通过，41次真实运行仍有超长、覆盖和语义失败；公共搜索历史失败也未解决。下一步应由真实人工校准标签、补自然语言/条件反例，再研究新的覆盖或格式约束，不能仅靠继续堆提示词。

能够准确指出在哪些条件下有效、哪些地方失败、下一次怎样验证，才是可维护的工程项目。当前已完成本轮评估与修复要求，但没有理由把有限开发试验包装成全领域准确、生产隔离或全面防注入。

```powershell
uv run --offline --no-sync python scripts/benchmark_research.py run --execute --mode fixture --case mcp_stdio --strategy segments --repeats 1 --answer-chars 500 --corpus reports/evaluation-20261101/corpus-exposed
```

若你想确认全部代码规则，而不只是看一条流程，在项目终端运行`python -m unittest discover -s tests -v`；本项目通常写成`uv run --offline --no-sync python -m unittest discover -s tests -v`。完整回归和单个fixture不是同一个测试范围，运行合同测试通过也不等于模型事实准确。

### 16.4 第二次操作：用预设题做固定资料上的真实对照

中心2 → 选一道题，例如python_wait_for或mcp_logfiles → 环境选1“真实模型＋冻结网页” → 选择本次只改什么：

| 比较轴 | 实际配置 | 适合查什么 |
|---|---|---|
| 单配置 | segments＋standard | 先建立一份可复核基线 |
| 比较选段 | bm25 vs balanced，统一standard | 关键句是否被选到、哪一侧预算被占满 |
| 比较格式 | segments固定，standard vs compact | 同证据条件下是否减少复述、是否丢必答点 |

重复次数建议先1，确需观察波动再2；每页字符先2400，回答先500。终端对照一次只变化一个轴，不提供同时换两种选择器与两种格式的四宫格。后者难以定位原因；有需求可另设计明确实验，而不是误称单变量。

接下来会保存preview-plan.json并显示trial总数。例如比较格式、重复2次，就是四个trial，AB/BA顺序standard、compact、compact、standard；不是四道独立题，也不是精确四次模型请求——每题可能先请求工具再生成最终回答。缩稿在此向导中关闭，0模型重试。

**回车只保留计划，输入LIVE才调用真实模型。** 0搜索并不表示没有网络费用：frozen仍会把保存片段发给模型服务。该入口默认provider-default，不把DeepSeek的特殊thinking开关盲目套给其他服务。uv的offline仅限制依赖获取，不能阻止显式LIVE应用请求。

资料已在快照目录时不重新下载；要比较同资料就始终沿用该快照。相同URL的新版网页只能作为新环境另分组，不能偷偷替换旧HTML后声称只是改了选择器。

你也可以先读已有真实结果，无需再次付费：中心5选择`improvement-20261102/style-pair`，选c，再选mcp_logfiles第一对。原standard回答637字符，compact回答394字符；按500上限前者失败、后者通过。继续看原证据和标准，确认不是删掉“stdout通道”和“日志文件未规定”的关键范围才变短。这是0.37历史助手复核的开发结果，不是本轮新增人工结论。

### 16.5 第三次操作：有针对性地自定义问题与要求

先把目标写小。例如你不是笼统地测“Python懂不懂”，而是测“比较两个API时是否漏掉一侧取消对象”。中心3依次输入：

| 提示 | 一个可直接练习的输入 |
|---|---|
| 研究问题 | 比较asyncio.timeout与wait_for的取消对象和总等待时间 |
| 回答上限 | 500 |
| 必答点条数 | 2 |
| 必答点1 | 必须分别指出两个API取消的是哪个对象 |
| 必答点2 | 必须解释wait_for总等待可能超过给定超时 |
| 资料 | 1：已保存Python 3.13官方页 |

程序自动再加一条“主要结论有本次保存证据、正确层次引用和条件/否定范围”的支持标准。你的必答点属于coverage，即“答没答全”；自动项属于support，即“说出来的话有没有依据”。两者不能互相替代。

题库保存为新目录里的custom-suite.json，题号custom_question。**不要修改eval/research_suite.json来练习**：那会改变预设题与历史比较条件。终端会把字数约定追加到问题，运行时还取题目与配置上限的较小值；因此后来把CLI改为700不会放宽题目500上限。

接着选择运行环境与比较轴。第一次练操作可选环境4固定模型、比较格式、重复1次；这样只验证自定义题库能流过系统，不能验证答案水平。本轮实际这样走通了两种配置、各一份trial，全部保留待判定，见[自定义终端全过程](../reports/evaluation-ux-20261102/custom-terminal.txt)与[实际题库](../reports/evaluation-ux-20261102/custom/custom-suite.json)。

真正测上述问题时选环境1真实模型＋冻结网页，输入LIVE后才执行。想比较模型是否能把资料中的两个取消对象都答出来，就同时看两侧原文有没有进入content，再看答案，而不是只检查关键词“timeout”是否出现。

如果你的问题不属于Python或MCP，资料选3，填写一个可公开访问的HTML URL。frozen/fixture会先展示计划，只有输入FETCH才下载并保存HTML/hash，下载成功后重新展示带快照的计划，再确认模型执行。回车停在计划，不自动访问URL。FETCH只下载页面，LIVE才是模型执行，两者不同。

本向导一次自定义一题、一份HTML，适合定向定位；不支持PDF、登录、动态点击或自动把全部资料导入库。进阶多题/多来源可复制一份题库，用--suite指定；每题最多3个文档，ResearchSuite校验字段、题号和URL。新网页若重定向/私网解析/类型不符会按原获取边界失败，不自动换一页当同一证据。

### 16.6 如何复用自定义题，不要每次重新手写

中心5找到原批次，选r“复用某题和标准，建立新实验”，再选题与环境/比较轴。它读取原批次已经保存的suite.json，保留原问题和rubric，使用当前代码生成新计划和新批次；旧run/标签不覆盖。真实执行仍要LIVE，新资料下载仍要FETCH。

这适合“我只改了select_balanced，再跑同一道题”。若题目或标准也有变化，请中心3另建题库并说明新目标，不拿旧分数直接说新算法提升。若原快照缺失或hash不符，要恢复原件；不要把后来下载的新页改名放进去绕过验证。

不想用菜单时，可以复用本轮已保存的自定义题库，先只看计划：

```powershell
uv run --offline --no-sync python scripts/benchmark_research.py plan --suite reports/evaluation-ux-20261102/custom/custom-suite.json --case custom_question --mode frozen --strategy bm25 --strategy balanced --repeats 1 --answer-chars 500 --corpus reports/evaluation-20261101/corpus-exposed
```

真正运行时把plan换为run并显式加--execute；这会在frozen模式请求模型。终端向导的LIVE是UI防误触，普通CLI的明确执行参数是run --execute。题库路径、题号、模式和快照均应一致。需要多次重复先定次数，失败也保留，不通过不断执行挑最好答案。

### 16.7 怎样看结果、自己复核和生成成绩单

运行结束自动进入批次页；以后从中心5打开。批次页先给配置汇总，再列每个trial的序号、状态、字符数。**输入序号**打开这一次的完整回答与诊断，**c**看同题同重复号的A/B两份完整答案（顺序显示，含focus、字符和token），**s**生成Markdown成绩单，**o**打开最新成绩单，**r**复用题目新建实验，**0**返回。

| 看到的项目 | 怎样理解 | 下一步 |
|---|---|---|
| saved / completed | 记录已保存、模型流程结束 | 还要看程序门槛和语义标准 |
| 门槛通过 | 长度/引用可用性/预算等机械规则满足 | 不表示每项事实都有支持 |
| 完整复核0、待判定 | 没有人完成逐项语义判断 | 去单次菜单3看标准，必要时4填写 |
| 综合失败但语义未完成 | 已知门槛如超长失败，足以判任务未满足 | 门槛和未评语义分别保留，不误说已判所有事实错 |
| 标签/绑定无效 | run、题目或复核结构不一致 | 恢复原件或修复复核文件，别改hash绕过 |
| worker_failed / process_deadline / not_run | 没有正常保存或还未执行 | 看index/日志，保留分母，不当知识准确率 |

单次trial页中：1看工具trace，2看保存证据，3看当前标准/标签/理由，4亲自填写复核，5/6/7打开report/run/目录。查看操作沿用原默认程序隔离方式。终端会清理外部文本控制序列；实际正文仍原样保存在run里用于定位。

亲自复核时，先完整读答案和保存证据，再填署名。每条标准选择1满足、2不满足、3尚不能判断，默认3。已判断的必须填写理由；支持类“满足”还须选择实际保存的摘要或正文，粘贴其中的连续摘录，回车可使用该保存段落整体定位。这里的摘录匹配只核对位置，仍由你判断它是否支持结论。

输入SAVE才保存task-review.json，回车取消，q取消当前设置。已有复核会先原样存入review-history，不覆盖run和原答案；因此亲自改历史助手判断后仍可追溯原版本。菜单如实把你的操作记为human，但字段不认证身份或独立性；改两个名字不等于两位独立审核者。若不能判断就保持null，整个复核仍不完整。

保存后返回批次页会重读最新标签，再选s生成新assessment Markdown，选o打开。报告按题号列原问题、完整回答、未通过门槛、失败标准和标准内的改进建议；不是只给一个总分。s不会重新研究，旧assessment也不会删掉。CLI等价只读评分：

```powershell
uv run --offline --no-sync python scripts/benchmark_research.py score --batch reports/evaluation-ux-20261102/fixed/batch
```

score的退出0表示全部判完且通过；3表示存在失败或待判定，是有效结果；2表示绑定/复核结构错误。终端run操作的退出0只表示该执行批次没有基础设施故障，语义仍可能全待定或失败，不能把两个阶段的0都叫“答对”。

普通自评与独立盲评也不同。中心的单次复核适合自己定位，能看到配置；需要两位实际审核者独立判断时，用现有blind-prepare导出隐藏显式策略的副本，private-map不一起给出，完成后blind-check。该工具仍不调用模型，空表不是人工gold。

### 16.8 从结果得到改进思路：沿同一份数据往回找

| 具体表现 | 先看哪里 | 有针对性的下一步 | 怎样验证没有掩盖问题 |
|---|---|---|---|
| 0正文或搜索异常 | trace中的error_code、backend_attempted、预算 | 先处理配置/网络/读取边界 | 别先改提示词“让模型自信回答”；保留原失败 |
| 比较漏掉一个API | trace的focus与菜单2的content | 若关键句没返回，比选段/分配/前缀开销 | 固定同HTML/字数；检查双方条件及完整代码 |
| 关键句已返回但没答 | 完整回答与必答rubric | 比写作格式或逐项覆盖指引 | 不靠扩大预算或把漏项删出标准 |
| 回答很短但错误/扩大范围 | 原证据、否定/版本/例外 | 更精确地对齐结论范围；补反例 | 语义检查不能由字数替代 |
| 答全但超过500字符 | answer_chars、必要信息与重复内容 | 比standard/compact；另做显式缩稿实验 | 保留条件、引用及额外请求；不可直接截断 |
| A/B只有一次好 | 同题repeat的所有trial | 预先规定重复次数，必要时扩展独立新题 | 不只展示成功样例，不合并异质批次准确率 |
| 评审意见不同 | 原标准、理由与引用 | 先明确标准/证据范围，再裁决 | 不简单按多数或把助手改名当人类gold |

以mcp_logfiles的637→394字符旧样例为例：先确认两份都实际读到了stdout/stderr条款，再看两份回答是否都没有从stdout禁令扩大为禁止写任何文件，最后才说该开发样例compact更简洁。它不能证明所有问题都会更准确，也不能忽略比较题仍失败的记录。

以自定义两个取消对象为例：如果tool返回只有wait_for定义，就优先研究多点取证；如果已经含“取消当前任务”而答案仍写“取消内部协程”，应研究模型理解/输出范围，而不是继续增加检索。新增改动后用中心5的r复用原题和快照，保留新旧两批，比较门槛、语义、token和失败原因。

### 16.9 抽取对照怎样查看，和问答怎么配合

本轮实际选“timeout_waitfor”场景中balanced/2400那一行，检查两侧取消与外部捕获条件，见[抽取操作全过程](../reports/evaluation-ux-20261102/extraction-terminal.txt)。生成的120行保存在[本次抽取结果](../reports/evaluation-ux-20261102/extraction-example/extraction/results.json)，全部有界。中心5还可输入e再查看已有抽取，无需再次计算。

### 16.11 整套终端逐页图鉴：每一项是什么意思

本节把主页、单次研究、历史查看和评测中心全部放在一起。下面的菜单文字已按0.39当前代码的实际调用重新核对；数字清单来自本机当时的保存材料，所以历史顺序、题号行及路径可能与你稍后看到的不同。`Pxx`只是说明文件内部的页面样本编号，不是终端里要输入的指令。

这次共采集58组菜单/输入状态，覆盖terminal.py与evaluation_terminal.py中全部52个业务输入调用位置。采集只进入设置、读取原件及取消路径；真实模式的确认是页面样本，没有调用真实模型、下载网页、SAVE复核或打开外部编辑器。输入错误、无数据等提示在本节末尾另列。当前采集原件在reports/completion-20261109/menus-final.json；11-03原件保留为历史，维护者可据此对照源码。

**先认清页面层级。** 主页1/2属于“一次研究”，主页3看单份run；主页4进入“评测中心”，它按一题多配置/多次尝试组织批次。一次研究的查看页和一次评测试验的查看页不是同一页，相同数字可能做不同的事。需要复核、A/B与成绩单时进入评测中心。

| 词语 | 从零理解 | 例子 |
|---|---|---|
| Agent / Session | 模型与工具的研究循环 / 本题的来源和预算状态 | 每次trial新建，不继承上一题证据 |
| run | 一次实际研究记录，含答案、证据和trace | 一份run.json与report.md |
| task / trial / batch | 一道题 / 该题一次尝试 / 计划中的一组尝试 | 1题×2配置×2次＝4个trial的批次 |
| trace | 应用实际工具调用记录 | 有没有read_page、focus是什么、是否失败 |
| rubric | 判断题目完成与否的逐项标准 | 必须说明wait_for取消aw |
| source / snippet / page | 来源 / 搜索服务摘要 / 本次保存的正文片段 | URL已登记不表示已经有正文 |
| key / provider | 访问服务的凭据 / 实际服务提供者 | 模型key与Tavily搜索key不同 |
| token / 字符 | 模型处理的文本单位 / 程序计数的文字单位 | 1800 token不等于1800汉字；500字符含引用标记 |
| config / variant | 设置 / 一种具体实验配置 | segments__compact是选段＋写作格式，不是第二个Agent |
| HTML / DOM | 网页结构文本 / 浏览器解析后的页面结构树 | HTTP直接解析HTML；隔离浏览器从静态DOM取内容 |
| JSON / Markdown | 结构化数据文本 / 易读的轻量排版文本 | run.json放字段，report.md放回答，assessment-*.md放成绩 |
| stdin / stdout / stderr | 进程的标准输入 / 输出 / 错误通道 | stderr也可用于普通日志，有文字不自动代表失败 |
| stdio / SSE | 标准输入输出通信 / Server-Sent Events服务端事件流 | MCP传输语境中的不同通信形式，不是模型种类 |

**输入规则。** 数字和c/r/s/o/e按菜单输入，字母选项用小写；例如大写C不是当前c菜单项。回车采用`[默认值]`，但没有默认值的必填文本不能留空。q或Q在输入处取消当前操作：单次研究回主页，评测内部回评测中心，未SAVE的标签丢弃、已经写出的题库/计划保留。0只有页面明确列为返回，或数值范围包含0时才有对应含义，不能把任何输入框的0都当返回。个别共用输入提示仍写‘q返回主页’，在评测内部按实际控制流回评测中心。LIVE/FETCH/SAVE大小写均可，回车通常表示不执行该动作。

Ctrl+C退出整个终端；Windows Ctrl+Z后回车表示结束输入。若正在执行任务，已保存材料保留，当前任务未必产生完整run，不应把它误说成已完成。下面按“进入路径→页面→每项解释→例子”阅读即可。

| 每次trial折叠块 | 点击展开问题、完整回答、逐项标签/理由/建议 | 把汇总数字追溯到具体回答和原标准 |
| criteria.csv | 用Excel等打开，按variant、dimension、met筛选 | 一行是一条标准，找哪一侧比较经常漏、支持项是否失败 |
| matrix-N.csv | 从网页注明配置名的链接进入 | 同配置每次trial×全部标准的宽表，定位反复失败点 |
| diagnostics.json | 程序或编辑器查看 | 精确字段、原执行/当前诊断指纹、各原件hash，便于复核与二次分析 |

长表例子中，task_id=python_compare、dimension=coverage、met=false，含义是审核者认为该次回答没有满足这条覆盖标准；还应读reason、description、next_action以及reviewer_kind。false不是“检索必然失败”，也不是模型自动评分。

宽表的列名含task_id:criterion_id，防止不同题都叫point_1时混淆。true/false是有效复核已有判断；null表示尚未判断、未运行或无效复核（长表另有label_state）；n/a表示这一行是别的题，该列不适用。不要把空白、null、n/a都替换成0来求准确率。

#### 16.12.4 L1～L5怎样帮助改进，又有哪些不能自动判断

| 层 | 从零理解 | 需要看的材料 / 一个例子 |
|---|---|---|
| L1证据获取 | 搜索或抓页有没有真的成功 | search_error、page_error、无保存证据；先排网络/来源，不先调写作提示 |
| L2证据选择 | 原网页有，选段没有保留 | 拿冻结HTML对比保存片段；原文有取消完成条件，但预算没有选中它 |
| L3上下文交付 | 选中内容是否真正交给模型 | 核对观察内容/省略限制；不能只看保存了segments就声称掌握完整请求 |
| L4回答生成 | 证据已经可用，表达仍漏答、扩大、超长 | 比较原答案与原证据；先固定一个变量，如standard/compact |
| L5评测 | 标准、标签或门槛是否判错 | 复核引用错文件，或把分析性攻击引用误当服从；应裁决而非改旧答案 |

当前程序只给症状与排查候选：coverage失败列L2/L3/L4，非法复核列L5候选，超长列L4候选。failure_layer仍为null、confirmed_failure_layers为空，表示根因尚未由人确认。这不是缺失值需要自动补齐；信息不足时保留未知才可信。不同候选计数可重叠，不能相加成总失败数。

实际改进例子：先筛python_compare的coverage失败→展开答案→读原保存证据→若关键限定在原HTML而不在片段，研究focus/selector；若片段已经含关键限定，研究回答范围和写作。下一轮只改一个变量，预先固定新问题/标准/预算/重复数，保留失败，不为了得到漂亮表格反复重跑。

#### 16.12.5 固定流程、干净源码与CI怎样演示

没有真实key也能演示完整链：新环境按README安装，restore_test_fixtures.py恢复31份固定公开原件，verify_source.py跑local/MCP/固定批次/诊断四步。输出summary.json的passed只说明程序检查通过；fixture问题的语义标准仍null。源码包包含examples及固定包，不包含全部历史reports。

CI是持续集成：代码push/PR后GitHub按配置自动检查；coverage记录测试执行的语句与分支。本轮441项离线回归通过，应用源码本进程语句90.1%、分支83.3%、综合88.0%，不包含子进程和上游SDK，也不是回答正确率。CI配置及同命令本地验证已有，远程runner尚未执行，不能贴虚构绿标。完整安装/报告操作仍集中在统一验收指南10节。

#### 16.12.6 面试如何把这轮讲成一项贡献

“我发现只有大量trace不够，还需要把失败转成可定位的实验输入。于是复用原绑定检查器，做了一个只读批次诊断：分开普通问答与对抗，导出逐标准矩阵，把症状和根因候选分开。我也实际验证干净目录，修掉历史测试对原目录的依赖。没有因此声称模型更准，因为这一轮没有改生成算法或新增真实质量实验。”

追问时打开diagnostics.py说明三件事：为什么无效复核不能进入矩阵、为什么null不能变零、为什么L2/L3/L4不能凭漏答自动归因。再用test_diagnostics.py展示坏绑定、CSV公式、HTML脚本和ZIP越界的反例。Git基线、CI、coverage是支撑可信交付的工程工具，不替代对Agent循环和证据契约的理解。
